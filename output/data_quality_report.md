# Data Quality Report

Generated by running `python -m src.pipeline` against the datasets in `data/`.
This report documents every issue the pipeline's validation gate found, how
`transform.py` resolved it (or why it was deliberately left unresolved), and
the reasoning behind each decision. Full run-by-run detail is in
`output/pipeline.log`.

## Methodology

The pipeline validates data **twice**: once on the raw CSVs (`extract.py`
output) and again after cleaning (`transform.py` output). The first pass
tells us what's wrong with the source data; the second is a quality gate
that confirms cleaning actually worked and surfaces whatever couldn't be
fixed. Two ground rules drove every cleaning decision:

1. **Never drop a row just because one field is unrecoverable.** A sale or a
   piece of feedback is worth more than a spotless table. Unrecoverable
   fields are left `NULL`/`NaN` and excluded naturally by downstream
   aggregations (`AVG`, `SUM`, `.corr()` all skip nulls).
2. **Never fabricate a value.** If a field can't be recovered from other
   columns in the same row (e.g. recomputing a missing `total_amount_usd`
   from `quantity_kg x unit_price_usd`), it's left null rather than guessed.

## Issues found and how they were resolved

### products.csv

| Issue | Rows | Resolution |
|---|---|---|
| Exact duplicate row (`P002`, every column identical) | 1 | Dropped — a true duplicate carries no new information. |
| Null `product_name` (`P029`) | 1 | Filled with `Unknown (P029)` so the row stays usable for category/revenue aggregation without inventing a name. |
| Null `num_ingredients` (`P024`) | 1 | Left `NULL` — no other column can derive an ingredient count. Excluded naturally from the complexity-vs-satisfaction analysis (Q3). |
| `num_ingredients = -5` (`P033`, "Oriental Spice") | 1 | A negative ingredient count is meaningless. Set to `NULL` rather than guessing the intended value (e.g. assuming a sign flip). Found while building `sql/queries.sql` — it was silently skewing Q3's grouped averages before this fix. |
| Inconsistent `status` casing (`active` vs `Active`) | 1 | Normalized via `.str.capitalize()`. |
| Non-ISO `launch_date` format (`15-12-2023` mixed into `YYYY-MM-DD`) | 1 | Parsed correctly with `pd.to_datetime(..., format='mixed')` instead of the default parser, which was silently coercing it to `NaT`. |

**Residual issue:** `num_ingredients` is `NULL` for 2 products (1 originally
missing + 1 invalidated negative value) — genuinely unrecoverable, not a bug.

### sales_transactions.csv

| Issue | Rows | Resolution |
|---|---|---|
| `transaction_id = 'T011'` reused across two rows with **different** `transaction_date`, `quantity_kg`, and `total_amount_usd` | 1 | This is an ID collision, not a duplicate — two real, distinct transactions. Renamed the second occurrence to `T011-DUP1` instead of dropping it, preserving both sales. Safe to rename because nothing else references `transaction_id` as a foreign key. |
| Null `customer_id` | 1 | Filled with `'UNKNOWN'` (explicit, filterable placeholder — not a fabricated customer). |
| Null `total_amount_usd`, but `quantity_kg` and `unit_price_usd` both present | 1 | Recomputed as `quantity_kg x unit_price_usd` — this is a legitimate derivation, not a guess. |
| `product_id = 'P999'`, which doesn't exist in `products.csv` | 1 | Left as-is. The sale is real revenue; dropping it would understate revenue totals. It's excluded from category-level breakdowns (`sql/queries.sql` Q1 buckets it under `'Unknown/Unmatched Product'` via `LEFT JOIN`) rather than silently vanishing. |
| Non-ISO `transaction_date` format (`7/15/2024`, `07-18-2024` mixed into `YYYY-MM-DD`) | 2 | Parsed correctly with `format='mixed'`. Without this fix, both transactions would have dropped out of any date-based aggregation, including the quarterly trend analysis (Q4). |

**Residual issue:** the `P999` orphan reference — by design, see above.

## Residual known issues (by design, not bugs)

These 4 issues remain in the loaded database on purpose, because "fixing"
them would mean fabricating data:

1. `products.num_ingredients` is `NULL` for 2 products.
2. `sales.product_id = 'P999'` has no matching product (1 transaction).
3. `feedback.quality_rating` is `NULL` for 1 record.
4. `feedback.product_id = 'P999'` has no matching product (1 record) — same
   orphan reference as in sales, from a different table.

Every business question in `output/business_answers.md` either naturally
excludes these rows (aggregations skip `NULL`) or explicitly surfaces them
(Q1's `'Unknown/Unmatched Product'` bucket) rather than silently dropping
data.
